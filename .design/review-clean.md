# 龙猫工厂 Longmao Factory 系统批判性评估

> 评估人：deepseek-v4-pro（子代理）
> 评估日期：2026-09-10
> 评估对象：`skills/longmao-factory/SKILL.md` + `memory/longmao-factory.md` + `projects/awwwards-photographer/.design/history.md`

---

## 一、总体评价

龙猫工厂是一个**设计得相当成熟**的 thin-router + 专用 engine 架构。它的核心价值在于：把「一句话需求」拆解为「识别 → 澄清 → 参考收敛 → 引擎执行 → 量化验收 → 记忆沉淀」的完整闭环，并且用真实的 retro-musician（4 轮 baton）和 awwwards-photographer（4 轮 baton）两个项目做了实战验证。

这已经不是一个"占位 skill"，而是一个**有实战战绩、有硬性红线、有量化交付门槛**的工程系统。smell 的问题不在于"有没有"，而在于"哪些约束是纸面约束、哪些真正被执行了"。

---

## 二、路由逻辑评估

### 优点

1. **触发词表 + 复杂度判断双保险**：路由表包含"触发词"和"输出产物"两列，复杂度判断又单列了 5 个 baton 触发条件，覆盖了"提示词简略/页面>3/有用户流程/模块依赖/用户要求分阶段"五类场景。这是合理的。
2. **拆分维度判断清晰**：展示型网站按页面拆、工具型网站按功能模块拆，且给了一句"不确定时优先按功能模块拆"的兜底规则。这条兜底规则很关键，避免了路由时卡死。
3. **优先级拆分规则存在**：多类型混合时"先交付核心产物，比赛设计作为独立后续任务"。

### 问题

1. **触发词表与复杂度判断存在边界模糊**。例如"帮我做个数学建模作品展示网站，深色主题"被示例归为「简单」；但如果这个网站有 4 页 + 交互，按复杂度判断又该走 baton。"提示词完整"这条判断标准太主观——"完整"的阈值没有量化。
2. **"比赛设计"引擎是占位状态**。memory 里明确写着"占位，待跑通"，SKILL.md 里却写了一整套 competition loop 流程。这会造成路由到一个尚未验证的引擎，交付质量存疑。
3. **路由表缺少"失败回退"路径**。如果任务识别错误、或者澄清后用户改口，没有定义如何重路由。实战中 "awwwards-photographer" 的四轮都很顺，但历史上并没有记录"识别错误→重路由"的案例。

## 三、taste-skill 集成评估

### 优点

1. **"设计增强层（可选）"的定位非常正确**。明确声明 taste-skill 是"设计规范层，不能替代 ultimate-frontend-design 的代码生成能力"。这个边界避免了两个 skill 抢活。
2. **冲突解决优先级表写得很硬**：用户指令 > taste-skill > ultimate 默认；技术栈以 ultimate 为准；字体/颜色/布局禁令以 taste 为准。这是难得的"明确仲裁规则"，大多数 agent 工厂根本做不到这一步。
3. **"注入方式"克制而正确**：不是把整个 taste-skill 塞给 ultimate，而是"提取关键约束到 DESIGN_BRIEF.md 的「设计约束」章节"。这避免了 prompt 污染。

### 问题

1. **taste-skill 启用是"可选"的，但 anti-slop 是"必达"的**。这里有个逻辑裂缝：`4.5 视觉独特性`把"非默认字体/非默认色彩/非对称布局/禁用 AI 三件套"列为**硬性交付门槛**，但 taste-skill 却是"满足条件才启用"。也就是说，不启用 taste-skill 时，ultimate 引擎能否单独满足这些 anti-slop 门槛并未验证。retro-musician 和 awwwards-photographer 的产物都合格，但**我们不知道该归功于 ultimate 的能力，还是 taste-skill 的注入，还是两者缺一不可**。
2. **子 skill 选择表残缺**。「默认 anti-slop，设计感更强」→ `design-taste-frontend`，但其他子 skill（`imagegen-frontend-web`、`full-output-enforcement`、`stitch-design-taste` 等）没有进入这张表。表里列出的路径和 available_skills 清单有出入，容易选空。
3. **冲突解决优先级第 4 条"如仍有模糊，在 DESIGN_BRIEF.md 显式声明"是纸面规则**。没有定义"声明格式"，也没有定义"谁来最终拍板"。实战中这条大概率被跳过。

## 四、baton 模式评估

### 优点

1. **文件结构完整且自洽**：`SITE.md / DESIGN.md / DESIGN_BRIEF.md / REFERENCES.md / next-prompt.md / history.md` 六件套覆盖了站点地图、视觉系统、风格简报、参考来源、当前任务、历史记录。从 awwwards-photographer 的 history.md 看，这个结构确实被落地执行了（4 轮，每轮有明确产物和 `npx vite build` 验证）。
2. **执行规则里的"每轮只做一件事，不跨轮偷跑"是极好的约束**。这直接防止了意识流式的一口气生成全家桶，是 baton 模式最值得保留的一条。
3. **"每轮开始读取 .design/ 下所有文件，不依赖会话记忆"** 是对 agent 失忆症的准确对冲。

### 问题

1. **awwwards-photographer 的 history.md 暴露了一个实际偏差**：history 里记录的是 `src/App.tsx / src/Work.tsx / About.tsx / Contact.tsx`，**没有记录 `.design/` 六件套的更新情况**。SKILL.md 要求"每轮结束更新 history.md：记录完成内容、已知问题、下轮计划"，但这份 history 只记了"完成内容"，**"已知问题"和"下轮计划"两列是空的**。这说明 baton 的"已知问题传递"机制在执行时被弱化了。
2. **next-prompt.md 的"下一轮准备做什么"与 history.md 的"下轮计划"职责重叠**。两处都需要写"下轮计划"，容易不一致或漏写。
3. **拆分维度对"混合型网站"处理不足**。一个既有展示页又有用户流程的网站（比如"摄影师网站但带客户登录约拍"），按页面拆还是按功能拆？"优先按功能模块拆"的兜底可能破坏展示型的视觉连贯性。
4. **没有定义 baton 模式的"终止条件"和"轮次上限"**。如果用户一直说"再改改"，理论上可以无限轮。缺少"连续 3 轮无实质进展就停下来总结问用户"的熔断规则。

## 五、交付标准评估

### 优点

1. **量化门槛做得非常硬**。`4.1 可用性 / 4.2 正确性 / 4.3 视觉 / 4.4 性能 / 4.5 视觉独特性` 五张表都有"通过标准"和"验证方式"两个维度，不是空泛的"要好看"。
2. **具体的数值指标**（1440px/375px 截图、对比度 4.5:1、单文件 ≤10MB、`font-display: swap`）可以直接执行，可测可判。
3. **"失败必须修复或取得用户确认"** 给了交付一个诚实的出口。

### 问题

1. **标准的可执行性存疑**。`4.3 视觉` 要求"Playwright/浏览器 DevTools 截图"验证，但 SKILL.md 里没有定义"谁来跑 Playwright、跑出截图后谁来判断合格"。awwwards-photographer 的 history 里**只有 `npx vite build` 通过，没有任何截图/对比度/移动端验证记录**。说明这批标准里，实际被执行的可能只有"build 通过"这一条。
2. **`4.5 视觉独特性`的"验证方式"全是"截图人工检查"**。而 agent 工厂恰恰没有稳定的"人工检查"环节——谁来当这个"人"？如果由生成引擎自我检查，等于自证清白。
3. **`4.4 性能`里"单文件 ≤10MB 或总包 ≤5MB"与"非默认字体（本地 fallback）"存在矛盾**。本地字体 skb 通常几百 KB 到几 MB，多套字体很容易逼近 5MB 总包上限。retro-musician 用了 4 套字体，最终 JS 208k/CSS 16k，字体体积未披露——这可能是最接近超标的一环，但没人记录。
4. **交付清单与回顾缺失**。交付清单要求"下一步建议"，但整个系统没有"交付后回顾"环节——用户拿到产物后的真实反馈、是否部署、是否复用，都没有回流到 memory。

## 六、防带偏规则（Hard Rules）评估

三条 Hard Rule（新项目重新澄清视觉 / 参考只用于流程不用于设计 / 参考搜索先于代码生成）**是这套系统里最有价值的部分**，直接针对 agent 工厂最典型的两个病：**风格惯性复用**和**跳过前置收敛直接生成**。

但有个隐患：**"参考只用于流程不用于设计"与"参考搜索收敛风格"之间存在天然张力**。规则说"不复制视觉风格"，步骤又说"筛选 2-3 个可复用点（结构、布局、交互、信息层级）"。结构/布局/交互本身就在塑造视觉风格。这条边界在实操里非常容易滑向"抄了布局却说只是参考结构"。需要一个更具体的"可复用/不可复用"判定示例。

## 七、具体改进建议（按优先级排序）

### P0（影响交付质量，建议立即做）

1. **给 baton 的"已知问题传递"建立强制执行钩子**。把 history.md 模板改成强制三列：`完成内容 / 已知问题 / 下轮计划`，后两列不可为空（可写"无"）。因为 awwwards-photographer 已经暴露了"只记完成、不记问题"的滑坡。
2. **把验证从"纸面"变成"可执行的验证脚本/清单"**。至少定义：build 通过之外，还要产出 `dist/` 后跑一次双端截图（可用 `browser` 工具或 Playwright CLI），并在 history.md 里记录"桌面 1440px ✅ / 移动 375px ✅ / 对比度 ✅"。否则 4.3/4.5 的"截图人工检查"形同虚设。
3. **明确"简单 vs 复杂"的量化判据**。把"提示词完整"替换为可判的客观条件，例如：用户消息里明确给出了 ≥2 个页面结构 + ≥1 个视觉关键词 → 简单；否则 baton。消除主观判断。

### P1（影响系统一致性）

4. **补齐 taste-skill 子 skill 选择表**，与 available_skills 实际清单对齐，并标注每个子 skill 的"是否已验证可用"。避免选到路径为空或不存在的 skill。
5. **解决"anti-slop 是硬门槛、taste-skill 是可选增强"的逻辑裂缝**。二选一：要么把 anti-slop 门槛的达成责任明确指派给 ultimate 引擎（并验证它单独做得到），要么把 taste-skill 的启用从"可选"改为"默认（除非用户明确不要）"。
6. **合并 next-prompt.md 与 history.md 的"下轮计划"职责**。建议：next-prompt.md 只存当前轮任务，history.md 只做已完成记录，"下轮计划"只出现在 history.md 末尾一行，消除双写不一致。
7. **给 baton 增加熔断规则**：连续 3 轮无实质新增（build 通过但功能退回）→ 停止并总结问用户。

### P2（长期优化）

8. **把"比赛设计"引擎从占位状态升级**或从路由表中降级标注为"Beta/未验证"，避免路由到空架子。
9. **增加"交付后回顾回流"环节**：用户反馈、是否部署、是否复用的信息回流 memory，形成真正的经验闭环，而不是每次从零澄清。
10. **补充"可复用/不可复用"的判定示例**，软化"参考只用于流程"与"参考收敛风格"之间的张力。
11. **考虑在 Hard Rules 里加一条"字体体积预算"**：多套本地字体时，记录每套字体的体积，确保 ≤5MB 性能门槛真实可达。

---

## 八、结论

龙猫工厂是**一个架构正确、红线清晰、已有双项目实战验证的高质量 agent 工厂 skill**。它最大的成就是：把"抗 AI 廉价感"和"防止风格惯性复用"这些最难落地的目标，转化成了可检查的量化门槛和 Hard Rules。

它当前最需要补的不是"更多规则"，而是**规则与执行之间的闭环**——尤其是 `4.3/4.5` 的视觉验证（截图/对比度/移动端）在实战 history 里是缺失的，以及"已知问题传递"在 baton 中被弱化。缩短"写下来的标准"和"真正执行的验证"之间的距离，是它从"好 skill"走向"可靠系统"的关键一步。
